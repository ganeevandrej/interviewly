# Архитектура проекта Interviewly

Проект строго следует методологии **Feature-Sliced Design (FSD)**. Код разделен на слои, расположенные в жесткой вертикальной иерархии зависимостей. Компоненты на верхних слоях могут импортировать код только из нижележащих слоев.

### Направление потока зависимостей:

`app (Next.js) → views → widgets → features → entities → shared`

_Слой `server` вынесен за рамки клиентской иерархии зависимостей. Глобальное состояние (`store`) интегрировано в архитектурные слои._

---

## Ключевые архитектурные правила

1. **Плоская структура слайсов:** Все слайсы внутри слоев `views`, `widgets`, `features` и `entities` ДОЛЖНЫ лежать строго на одном уровне вложенности (в корне папки слоя). Вложенность слайсов друг в друга строго ЗАПРЕЩЕНА (нельзя делать `features/project/create/`). Для группировки используйте префиксы в kebab-case (например, `features/project-create/`).
2. **Фиксированные технические сегменты:** Внутри любого слайса разрешено использовать ТОЛЬКО стандартные папки-сегменты:
    - `ui` — визуальные компоненты, разметка, стили.
    - `model` — бизнес-логика, локальный стейт, селекторы, типы данных слайса.
    - `api` — эндпоинты, запросы к бэкенду.
    - `lib` — инфраструктурный код, хелперы, утилиты слайса.
3. **Публичный интерфейс (Public API):** Каждый слайс обязан иметь файл `index.ts` на своем корневом уровне. Он декларирует, какие элементы слайса доступны для внешнего использования. Импорты в обход файла `index.ts` (глубокие импорты) строго запрещены.
4. **Запрет кросс-импортов:** Слайсы, находящиеся на одном и том же слое, полностью изолированы друг от друга. Они не имеют права импортировать код «соседа» (например, `entities/project` не может ничего импортировать из `entities/story`).
5. **Чистая навигация — это НЕ фича:** Элементы интерфейса, которые просто выполняют роль ссылки или перенаправляют пользователя на другой URL (через Next.js `<Link>` или `router.push`), не содержат уникальной бизнес-логики. Они остаются внутри сегментов `ui` родительских страниц или виджетов и не выносятся в слой `features`.

## Иерархия слоев приложения

### 1. Слой `app`

Отвечает за инфраструктуру Next.js App Router, маршрутизацию и базовую инициализацию приложения.

- **Содержимое:** Маршруты Next.js (`src/app/**/page.tsx`), корневые файлы разметки (`layout.tsx`), глобальные провайдеры (MUI ThemeProvider, Redux Store Provider), глобальные стили, а также системные обработчики ошибок (`error.tsx`, `not-found.tsx`).
- **Правило:** Файлы страниц `page.tsx` должны оставаться тонкими серверными компонентами (Server Components). Их единственная задача — получить данные с сервера (через слой `server`) и передать их в качестве пропсов в соответствующее FSD-представление из слоя `views`.
- **Текущее решение проекта:** на этапе модернизации клиента серверные `page.tsx` могут напрямую получать данные через функции слоя `server` и передавать их в `views` через `initial*` props. Эти props могут содержать клиентские представления серверных моделей Prisma; перенос загрузки чтения в RTK Query не является обязательным.
- **Граница интерактивности:** RTK Query на текущем этапе используется прежде всего для mutations. После успешной mutation клиентская страница вручную обновляет локальное состояние, созданное из `initial*` props. Это временно поддерживаемый паттерн проекта и не требует query endpoints для списков.

### 2. Слой `views`

Содержит слайсы полноценных экранов приложения. Отвечает за общую композицию интерфейса конкретного маршрута.

- **Содержимое:** Слайсы страниц приложения (например, `src/views/story-list/`).
- **Структура слайса:** Обязательно содержит папку `ui/` с главным компонентом страницы и локальными подкомпонентами, а также корневой файл `index.ts`.

### 3. Слой `widgets`

Крупные, автономные и композитные блоки интерфейса, собирающие воедино сущности и фичи.

- **Содержимое:** Глобальный каркас приложения (`AppShell`), панели настроек, сложные сетки элементов, независимые крупные панели (например, `src/widgets/question-manager/`).

### 4. Слой `features`

Интерактивные элементы и пользовательские действия, несущие прямую бизнес-ценность и меняющие состояние приложения.

- **Содержимое:** Формы создания, редактирования и удаления сущностей, кнопки отправки данных, процессы авторизации, интерактивные переключатели (например, `src/features/story-archive/`).

### 5. Слой `entities`

Доменные модели данных (бизнес-сущности), их типы и базовые компоненты отображения. Не содержат логики активных действий пользователя.

- **Содержимое:** Слайсы бизнес-понятий (`user`, `project`, `story`, `question`, `tag`).
- **Структура слайса:**
    - `ui/` — компоненты отображения (карточка проекта `ProjectRow`, ярлык `TagBadge`).
    - `model/types.ts` — **строгое место для хранения доменных типов сущности** (интерфейсы `Story`, `Project` и т.д.).
    - `api/` — эндпоинты RTK Query, специфичные для этой сущности (внедряются в базовый API через метод `.injectEndpoints()`).

### 6. Слой `shared`

Нейтральный и абстрактный фундамент кодовой базы. Полностью очищен от бизнес-логики проекта Interviewly.

- **Содержимое:** Общие UI-компоненты (UI-kit, например `GlassPanel`), базовые утилиты общего назначения, конфигурационные файлы.
- **`shared/api/baseApi.ts`:** Содержит корневой скелет `createApi` от RTK Query (конфигурация `baseUrl`, заголовки авторизации, обработка ошибок и базовые `tagTypes`). Конкретные эндпоинты здесь не описываются.
- **`shared/types`:** **Строгое место для хранения составных и сквозных типов**, которые связывают или комбинируют несколько сущностей одновременно.
- **Правило:** Код из `shared` изолирован. Он не может импортировать элементы из вышележащих слоев или слоя `server`.

## Изолированные инфраструктурные слои

### 1. Слой `server` (Server-only)

Выделенный слой для выполнения кода исключительно на стороне сервера.

- **Содержимое:** Клиент базы данных Prisma, файлы миграций, серверные хелперы, Zod-схемы валидации запросов и HTTP-хелперы.
- **Правило изоляции:** Клиентские компоненты (компоненты с директивой `'use client'`) **категорически не имеют права** импортировать код из слоя `server` или напрямую обращаться к Prisma. Взаимодействие происходит только через асинхронные HTTP-запросы (RTK Query), API-эндпоинты Next.js или через пропсы от серверных компонентов в слое `app`.
- На текущем этапе модернизации клиента существующая серверная модель и server-side чтение не перерабатываются. В рамках клиентской миграции исправляются только зависимости клиентских слоёв; серверные контракты и Prisma-код остаются без изменений.

### 2. Управление состоянием (`store`)

Концепция изолированной корневой папки `store` упразднена:

- Инициализация и конфигурация глобального хранилища (`configureStore`) находится в **`src/app/store/`** (или `src/app/providers/`), так как это инфраструктурная задача уровня приложения.
- Локальные слайсы стейта (редюсеры) и эндпоинты запросов распределяются по конкретным бизнес-слайсам в `entities/*/model/` и `entities/*/api/`.
