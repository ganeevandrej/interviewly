# Feature Development

Используй этот skill для реализации новых задач, фич и изменений существующей функциональности.

## 1. Понять задачу

Перед началом реализации определи:

- какое поведение необходимо добавить или изменить;
- какие части приложения затрагивает задача;
- какие технологии и области затрагиваются: UI, React, Redux, RTK Query, MUI, Next.js и т. д.

Не начинай писать код, пока не изучишь существующую реализацию.

## 2. Изучить проект

Перед реализацией:

- изучи связанные с задачей файлы;
- посмотри соседний код и существующие подходы;
- найди существующие компоненты, хуки, утилиты, типы и API, которые можно переиспользовать;
- при необходимости изучи зависимости и конфигурацию проекта;
- придерживайся существующих соглашений и архитектуры проекта.

Предпочитай развитие существующего решения созданию нового.

## 3. Выбрать необходимые skills

Перед реализацией определи, какие из установленных skills относятся к текущей задаче.

Используй только релевантные skills:

- `vercel-react-best-practices`
  Используй при разработке и изменении React-кода, особенно когда задача затрагивает rendering, data fetching, производительность, bundle size или повторные рендеры.

- `vercel-composition-patterns`
  Используй, когда задача затрагивает архитектуру компонентов, их API, композицию, переиспользование, передачу состояния или когда компонент начинает становиться слишком сложным.

- `model-redux-state/build-slices-and-selectors`
  Используй при создании или изменении Redux client state, slices, reducers, selectors, async thunks и normalized state.

- `manage-server-data/adopt-rtk-query`
  Используй при работе с серверными данными через RTK Query: API endpoints, queries, mutations, caching, invalidation и синхронизация данных с сервером.

- `material-ui-styling`
  Используй при создании или изменении стилей Material UI, выборе между `sx`, `styled()`, theme overrides и глобальными стилями.

- `material-ui-theming`
  Используй, когда задача затрагивает тему приложения, design tokens, palette, typography, spacing, breakpoints, color schemes или глобальную настройку компонентов MUI.

- `material-ui-nextjs`
  Используй только когда задача затрагивает интеграцию Material UI с Next.js: App Router, Pages Router, SSR, Emotion cache, fonts, Link или связанные настройки.

### Правила выбора

Не используй skill только потому, что соответствующая технология присутствует в проекте.

Одна задача может требовать несколько skills.

Например:

Создание обычного React-компонента на MUI:
`vercel-react-best-practices` + `material-ui-styling`

Создание сложного переиспользуемого компонента:
`vercel-react-best-practices` + `vercel-composition-patterns` + `material-ui-styling`

Добавление Redux client state:
`model-redux-state/build-slices-and-selectors`

Получение данных с backend:
`manage-server-data/adopt-rtk-query`

Изменение глобального визуального стиля приложения:
`material-ui-theming` + `material-ui-styling`

Перед использованием выбранного skill прочитай его инструкции и применяй только те рекомендации, которые относятся к текущей задаче.

Если рекомендации skill конфликтуют с существующей архитектурой проекта, сначала изучи причину существующего решения. Не переписывай архитектуру только ради соответствия skill.
```


## 4. Реализовать

Реализуй минимальное полное решение, которое закрывает поставленную задачу.

Во время реализации:

- переиспользуй существующий код, когда это уместно;
- предпочитай простые решения новым абстракциям;
- не реализуй функциональность «на будущее»;
- не выполняй несвязанный с задачей рефакторинг;
- не добавляй новые зависимости без необходимости;
- сохраняй существующие архитектурные границы.

Следуй KISS и YAGNI.

Применяй DRY, когда дублирование действительно представляет одну и ту же концепцию. Небольшое дублирование предпочтительнее преждевременной или неправильной абстракции.

## 5. Проверить

Запусти доступные и относящиеся к изменениям проверки проекта:

- typecheck;
- lint;
- tests;
- build.

Исправь проблемы, вызванные внесёнными изменениями.

Не скрывай ошибки через `any`, необоснованные type assertions, отключение lint-правил, игнорирование тестов и подобные обходные решения.

## 6. Упростить

Перед завершением ещё раз просмотри реализацию.

Проверь:

- можно ли переиспользовать существующий код;
- появилась ли ненужная абстракция;
- добавлен ли код, который не требуется текущей задачей;
- есть ли значимое дублирование;
- можно ли выразить решение проще;
- появились ли лишние state, effects, wrappers, helpers или dependencies.

Упрости решение, если это улучшает читаемость и не меняет требуемое поведение.

## 7. Провести review

Просмотри итоговый diff целиком.

Проверь:

- корректность;
- возможные регрессии;
- соответствие существующим паттернам проекта;
- лишнюю сложность;
- дублирование логики;
- неправильное владение состоянием;
- лишние effects и re-renders;
- проблемы с TypeScript;
- мёртвый или неиспользуемый код;
- случайные изменения, не относящиеся к задаче.

Исправь найденные проблемы.

## 8. Завершить

Кратко сообщи:

- Какие skills были использованы;
- что было реализовано;
- какие важные решения были приняты;
- какие проверки выполнены;
- что не удалось проверить, если такое есть.

Не пиши длинный отчёт без запроса пользователя.
